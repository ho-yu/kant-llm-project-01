# Step 06

<일반적인 이커머스 고객 문의와 셀러 업무 질문에 적절하게 답변할 수 있는 로컬 LLM을 비교·평가하여 가장 적합한 모델을 선정한다.>

## 1. 실험 설계

| | |
|---|---|
| 실행 | 로컬 모델 6개(A~F) × 질문 10개 × 각 2회 = **본 실험 120회** (완료) |
| 품질 채점 | 비교 대상 3개(C 금융 / D 코딩 / F 이커머스) × 10문항 × 2회 = **60블록** |
| 부가 테스트 | 3개(A 법률 / B 의료·바이오 / E 수학) — 성능 측정만 쓰고 채점·선정에서 제외 |
| 워밍업 | 모델당 1회. `phase=warmup` 으로 본 실험과 분리 집계 |

과제 필수 최소치는 로컬 후보 2개(40회)이며, 채점 대상 3개는 그 이상이다.
비교 대상을 3개로 좁힌 기준은 [step08.md](step08.md) 에 적는다.

실행 설정은 6개 모델에 동일 적용했다 — `temperature=0` / `num_predict=768` /
`num_ctx=4096` / `seed=0` / system prompt 없음. 실제 적용값의 근거는 원본 실행 기록의 `options`와 `system_prompt`다. 현재 코드는 v1 값을 옮긴 `data/config/execution_conditions.json`을 읽는다.

측정값·성공 여부는 이 파일에서만 나오며, 집계표의 모든 수치는

```bash
cd project1-python-start && uv run python 11_finish.py
```

진행률·검사 결과가 나오고, 아래 자동 생성 구간이 갱신된다.

## 4. 결과 해석

> 채점을 마친 뒤 직접 쓴다. 자동 생성 구간 **밖**에 쓴다.
> 수치를 옮겨 적지 말고, 그 수치가 무엇을 뜻하는지 쓴다.
>
> - 조건 6(평균 3.5 이상) 판정과 그 근거
> - 기준별로 갈린 지점 (A~E 중 어디서 차이가 났나)
> - 사례 유형별 차이 (정상 / 경계 / 정보 부족)
> - Run 1·Run 2 차이 — `temperature=0` 이므로 샘플링 변동이 아니라 실행 환경 변동이다
> - 대표 성공·실패 사례 (질문별 '관찰 메모' 에서 가져온다)
> - 한계: 10문항, 반복 2회, VRAM 8GB, 채점자 1인

저장 위치: `data/raw/local/runs.jsonl` (JSONL, 한 줄 = 한 회차)

| 과제가 요구하는 것 | 실제 필드 | 비고 |
|---|---|---|
| 실행 ID | `run_id` | `C_Q01_r1` 형식. 채점 블록 제목과 같다 |
| 질문 ID | `question_id` | Q01~Q10 |
| 모델 | `model_tag` | 양자화 포함 전체 식별값. `model_label` 은 표용 |
| 반복 회차 | `repeat` | 1 / 2 |
| 워밍업 여부 | `is_warmup`, `phase` | `phase=warmup` 은 본 실험 집계에서 제외 |
| 입력 전문 | `prompt` | |
| 원본 응답 | `response_text` | 가공하지 않은 그대로 |
| 성공 / 오류 | `status` | `success` / `error` — 호출 성공 여부만 뜻한다 |
| 오류 내용 | `error_type`, `error_message` | |
| 전체 응답 시간 | `elapsed_sec` | 요청 직전~응답 수신 직후. **TTFT 가 아니다** |
| 모델 로딩 시간 | `load_duration_sec` | |
| 출력 토큰 수 | `eval_count` | 입력은 `prompt_eval_count` |
| 생성 속도 | `tokens_per_sec` | `eval_count / eval_duration_sec` |
| VRAM | `size_vram_mib` | 응답 직후 `ps` 관측값. 최대치가 아니다 |
| 실행 설정 | `options` | 실제로 넘긴 값을 그대로 복사한다 |
| 실행 시각 | `timestamp` | ISO8601 |
| — | `measurement_notes` | 값이 없을 때 **사유**. 0 으로 채우지 않는다 |
| — | `done_reason` | `stop` / `length` — 한도에서 잘렸는지 |
| — | `processor` | CPU/GPU 적재 비율. GPU 이용률이 아니다 |
| — | `settings_version`, `questions_version` | 어느 설정·질문 판으로 돌렸는지 |

(모델 식별·제원), `vram_observed_at` / `system_prompt` / `retry_of_run_id` 가 함께 기록된다.

### 집계 시 반드시 표시할 것 (평가표 #5·#6)

- [x] 모델별 **호출 성공 수 / 전체 시도 수** → 표 첫 행. 채점 대상 3개 모두 20/20
- [x] 지표별 **집계 응답 수(n)** → 모든 값에 `(n=...)` 이 붙는다
- [x] 측정 불가 항목이 있으면 **사유** 기재 → `measurement_notes` + '실패 / 측정 누락' 표
      (채점 대상 3개는 결측 0건, 부가 Model B 는 14회 결측이 사유와 함께 남아 있다)
- [x] 워밍업 / 재시도 / 추가 실험은 본 실험 120회와 **분리 집계**
      → `phase` 로 구분. 집계 범위가 표 아래에 명시된다 (126건 중 120건)
- [x] 비교 대상 3개와 부가 테스트 3개를 **표에서 구분** → 표가 둘로 나뉜다.
      좁힌 기준은 [step08.md](step08.md) 에 적는다
- [x] **실패**(호출 오류)와 **측정 누락**(호출은 성공했으나 값 없음)을 구분
      → `status` 와 `measurement_notes` 가 서로 다른 축이다
- [x] **첫 실행의 로딩 지연과 로드된 상태의 응답 지연을 구분**
      → 모델당 워밍업 1회로 로딩을 흡수한다. 실측: 워밍업 평균 로딩 4.65초 →
        본 실험 평균 0.20초. 워밍업은 `phase=warmup` 으로 집계에서 빠진다
- [ ] **tokens/s 만으로 품질이나 사용자 체감 속도를 판단하지 않는다**
      → 생성 속도는 품질과 별개 지표다. 실제로 이번 결과에서 가장 빠른 모델(D 66.97 t/s)이
        품질 1위가 아니다. 서술할 때 속도와 품질을 같은 문장에서 인과로 엮지 않는다

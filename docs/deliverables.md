# 프로젝트 산출물 체크리스트

> 이 문서는 과제 요구사항("7. 프로젝트 주요 산출물", "8. 이번 프로젝트에서 중요하게 보는 것")을 기준으로,
> 실제 작업을 진행하면서 각 항목의 결과물 위치와 완료 여부를 직접 채워 넣는 작업용 문서다.
> 로드맵([docs/roadmap.md](roadmap.md))의 장기 계획이 아니라 **Phase 0(4일 프로젝트) 제출물**에 한정된다.

## 제출 방식

- 개인/팀 단위로 **GitHub 저장소 하나**에 모아 제출
- 비교표·최종 보고서는 README 안에 포함하거나 별도 파일로 연결 — 같은 내용 중복 작성 금지
- 발표는 제출한 실험 기록·선정 근거를 재사용

## 요구사항 충족도 평가표

> 판정 기준
> - **충족**: 필요한 작업과 증빙이 있고 결과를 설명할 수 있다
> - **보완 필요**: 작업은 했지만 기록/비교 조건/설명의 일부가 부족하다
> - **미수행**: 작업을 하지 않았거나 확인할 증빙이 없다
>
> 판정과 보완 사항은 근거가 되는 저장소 내 실제 파일/문서 경로와 함께 기록한다.

| 요구사항 | 관련 STEP | 수행할 작업 | 완료 기준 / 확인할 증빙 | 판정 | 근거 위치 |
|---|---|---|---|---|---|
| 1. 문제/요구사항 정의 | STEP 1~2 | 사용 사례를 정의하고, 필수 통과 조건과 선호 우선순위를 실험 전에 정한다 | 사용자/태스크/제약조건과 선정 기준이 정리되어 있고, 조건별 확인 방법과 우선순위를 설명할 수 있다 | | |
| 2. 후보 모델 조사 | STEP 3 | 서로 다른 로컬 후보 2개의 특성과 실행 가능 조건을 조사한다 | Model Card/License 출처, 모델 크기/Context/양자화, 실제 모델 태그/식별값과 후보 선정 이유가 기록되어 있다 | | |
| 3. 실행 환경/기록 확인 | STEP 4 | 두 후보를 Python으로 호출하고 결과 한 건을 파일에 저장한 뒤 다시 확인한다 | 모델별 기본 응답, Python/Ollama/주요 패키지/장비/설정 정보와 저장된 원본 기록을 확인할 수 있다 | | |
| 4. 평가 질문/기준 확정 | STEP 5 | 질문 10개와 기대 결과/품질 채점 기준을 정하고, Cloud용 5문항을 미리 선정한다 | 질문 ID/입력 자료/기대 결과 또는 확인 항목이 있으며, 정상/경계/정보 부족 사례와 동일 입력/설정 적용 기준이 정리되어 있다 | | |
| 5. 로컬 비교 실험 | STEP 6 | 로컬 모델 2개 × 질문 10개 × 각 2회를 실행하고, 모델당 워밍업 1회와 구분한다 | 본 실험 40회의 응답/설정/성공/오류 기록과 전체 응답 시간/로딩 시간/출력 토큰 수/생성 속도/VRAM 기록을 확인할 수 있다. 측정 불가 사유, 호출 성공 수/전체 시도 수와 지표별 n을 표시한다 | | |
| 6. 품질 평가/해석 | STEP 5~6 | 원본 응답을 동일 기준으로 채점하고 점수 근거와 대표 성공/실패 사례를 분석한다 | 점수의 근거가 응답 부분과 연결되고, 평균 및 집계 응답 수를 원본 기록에서 확인할 수 있다. 개인은 재검토, 팀은 교차 확인을 수행하며 실패/측정 누락을 구분한다 | | |
| 7. Local–Cloud 비교 | STEP 7 | Cloud 모델 1개에 공통 질문 5개를 각 1회 적용하고 로컬의 동일 문항 결과와 비교한다 | Cloud 응답/상태/시간/토큰 사용량/비용과 품질 평가가 있다. 반복 수 차이와 지표별 집계 응답 수를 표시하고, 실측 결과와 운영 조건 분석을 구분한다 | | |
| 8. 최종 모델 선정/발표 | STEP 8 | 두 로컬 후보의 필수 조건 충족 여부를 확인하고 우선순위에 따라 후보 1개를 선정한다 | 선택/탈락 이유가 요구사항과 실험 근거에 연결된다. 두 후보 모두 필수 조건을 충족하지 못하면 그 사실과 상대적으로 적합한 후보를 설명하고, 실제 도입 가능 여부/한계/운영 권고를 구분한다 | | |
| 9. 제출/재실행 확인 | 7장 산출물 | 개인 또는 팀 단위로 저장소 하나에 코드/환경/질문/원본 기록/비교표/선정 근거를 모은다 | README에서 실행 방법과 자료 위치를 확인할 수 있고 코드의 입력/모델/설정/저장 위치를 설명할 수 있다. 개인은 본인/팀은 팀원 한 명 이상의 재실행 기록이 있으며, 팀은 작업을 나눈 경우 참여 내용을 남긴다 | | |

> 답변 품질이 낮다는 이유만으로 "미수행"으로 판정하지 않는다. 실제 결과와 실패, 한계를 어떻게 설명했는지를 본다.
> 선택 실습은 위 표의 필수 항목에 포함하지 않는다.
